# Design

## Context

见 proposal.md（Why 部分）。当前仓库无任何代码，`openspec/specs/` 为空，技术栈与架构意图仅记录在 `openspec/project.md` 中——该文件是提示词级上下文，不参与 `openspec validate`，也不被 delta 追踪，因此对后续生成的代码没有强制力。本设计解决的问题是：**以什么方式把这些决策变成可校验的约束，以及它们如何被真正执行**。

## Goals / Non-Goals

**Goals:**

- 产出一组能被 `openspec validate` 校验、能被后续变更以 delta 形式引用的工程约束。
- 让约束颗粒度与业务能力对齐，使未来单个能力演进时不必改动整份规范。
- 明确约束的**执行机制**：靠什么保证它们不被静默违反。

**Non-Goals:**

- 不产出任何运行时代码或工程骨架（那是后续变更的事）。
- 不定义具体业务功能（推荐流、播放器、评论的业务规则留待各自的功能变更）。
- 不引入自动化 lint/静态检查工具链，本阶段只定义规则与人工核对点。

## Decisions

### 决策 1：按能力域拆分为 6 份独立 spec，而非一份总规范

拆分为 `backend/architecture`、`api/contract`、`data/platform`、`frontend/conventions`、`identity/auth`、`quality/testing`。

- **理由**：后续变更通常只触及其中一个域（例如"新增评论接口"触及 api 与 data），独立 spec 让 delta 精准落位，也能单独演进与评审。
- **备选方案**：写一份 `engineering-standards` 总规范 → 否决，因为任何一处修改都要整体 MODIFIED，delta 噪音大，且容易膨胀成无人阅读的万字文档。

### 决策 2：约束以"可检查的 MUST/SHALL 语句 + 场景"表达，而非描述性文字

每条要求都写成可被人工核对或命令验证的判据（如"MUST NOT 在 api 层执行业务 SQL"、"MUST 由 Snowflake 生成"）。

- **理由**：描述性文字无法判定是否满足，也就无法在评审中执行；写成判据后，评审和后续自动化检查都有明确依据。
- **备选方案**：写成风格指南式的建议 → 否决，等于没有约束。

### 决策 3：执行机制是"规范校验 + 人工核对点"，而非运行时测试

基线规范约束的是代码结构与工程决策，无法用运行时功能测试断言。执行方式定为：

1. 任何后续变更的 design 必须显式列出所触及的基线规范条目并逐条核对；
2. 变更归档前 `openspec validate` 必须通过；
3. 首个工程骨架变更中，把"目录结构与分层是否符合基线"作为显式验收任务。

- **理由**：在零代码阶段引入自定义 lint 规则成本过高且收益不确定；人工核对点在早期足够，等骨架稳定后再考虑把高频约束（如禁止 api 层写 SQL）固化为静态检查。
- **备选方案**：立即编写自定义 lint 插件 → 否决，过早工程化。

### 决策 4：与 `project.md` 的关系是"概述 → 硬约束"，冲突以 specs 为准

`project.md` 保留面向 AI 的总体说明（定位、技术栈、工作流），具体判据以 `openspec/specs/` 为准；两者冲突时 MUST 修改 `project.md` 使其与 specs 一致。

- **理由**：避免同一条规则在两个地方各写一遍、随后各自漂移。

### 决策 5：冲突时走显式 delta，禁止静默偏离

后续变更若确实需要违反某条基线约束，MUST 以 MODIFIED delta 修改该规范并说明原因，MUST NOT 在实现中绕开。

- **理由**：静默偏离会让基线规范在一两次迭代后失去意义。

## Risks / Trade-offs

- **规范过严，拖慢早期探索** → 缓解：任何一条都可以用 delta 修改，基线不是不可动的；评审时优先看是否阻碍首个骨架落地。
- **规范与实现漂移（写完没人看）** → 缓解：决策 3 的核对点为强制项，首个骨架变更会实际执行一次核对，验证这套机制是否可行。
- **部分条目当前无法自动验证（如"业务逻辑在 rpc 层"）** → 缓解：这些条目以评审判定为准，场景描述中已写明"评审或静态检查发现即判定违规"。
- **服务域划分可能过早固化** → 缓解：architecture 规范只锁定首批五个域与"新域需登记"的规则，推荐流等归属留作开放问题。

## Open Questions

- 推荐/信息流（feed）能力的域归属未定：可归入视频域，也可独立成推荐域。该问题不影响本基线规范的成立，留待首个涉及 feed 的功能变更时决定，届时以 delta 补充到 `backend/architecture`。
