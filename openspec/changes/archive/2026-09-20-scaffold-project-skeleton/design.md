# Design

## Context

见 proposal.md（Why）。四项骨架决策已由用户拍定：顶层 `web/` + `server/`；后端单一 Go module；各服务按域前缀直连、不引入 BFF；前端 `src/` 增加 `app/`（路由与 provider）与 `theme/`（Mantine 主题）。同时 `establish-baseline-specs` 已就分层、目录、响应结构等形成约束，本设计是这些约束的第一次实际落地——因此骨架完成后必须回头核对一次，验证约束是否可执行。

## Goals / Non-Goals

**Goals:**

- 交付能启动、能自检、目录位置明确的空骨架。
- 让基线规范中的分层与目录约束第一次被真实代码检验。
- 提供可复现的本地环境（中间件 + 启动命令），降低后续变更的试错成本。

**Non-Goals:**

- 不实现任何业务功能（推荐流、播放器、评论、搜索的具体逻辑）。
- 不实现鉴权细节，仅在 `common/` 预留中间件位置。
- 不搭建 CI/CD、不处理部署到服务器的流程。
- 不写数据库业务表，仅预留迁移目录。

## Decisions

### 决策 1：五个域一次性建齐，而非渐进创建

骨架阶段即建立 `user`、`video`、`interaction`、`comment`、`search` 五个域目录，每个域的 `api` 层提供一个 health 接口；`rpc` 与 `model` 目录同步创建并以占位文件保留。

- **理由**：基线规范已锁定首批五域，一次建齐可让骨架直接反映规范的完整性，也避免后续每次加域都改动骨架结构。
- **备选方案**：只建 `user` 与 `video` 两个域，其余按需再建 → 否决，会让骨架与规范不一致，且后续每次加域都要重复同样的结构决策。

### 决策 2：`rpc` 与 `model` 用占位文件保留，不预生成代码

骨架阶段不为 `rpc`、`model` 生成 goctl 代码，只保留目录与占位文件（说明该层职责与后续生成方式）。

- **理由**：没有业务实体时生成的 proto 与 model 必然是错的，生成后还要删；占位文件足以让目录结构与规范对齐，并提示后续如何使用。
- **备选方案**：用 goctl 预先生成示例 proto/model → 否决，会产生需要清理的噪音代码。

### 决策 3：使用 goctl 生成 api 层，不可用时以等价手工结构替代

优先用 goctl 生成各域 `api` 层（etc 配置 + internal/{handler,logic,svc,types}）；若环境无 goctl 或版本不兼容，则手写等价的最小结构，保持目录与命名一致。

- **理由**：go-zero 的目录与命名有约定，与 goctl 保持一致可减少后续摩擦；但不让工具链缺失阻断骨架交付。
- **备选方案**：全部手写 → 否决，后续 goctl 生成时会覆盖或冲突。

### 决策 4：中间件用 docker-compose 编排，应用进程本地运行

`deploy/docker-compose.yaml` 只编排 MySQL、Redis、RabbitMQ、Elasticsearch；前后端应用由 `make dev` 在本地直接启动。

- **理由**：本地直接跑应用便于断点调试与热重载，容器只承担难以本地安装的中间件。
- **备选方案**：应用也容器化 → 否决，早期调试成本高、收益低。

### 决策 5：健康检查只做结构化状态返回，不做依赖强校验

health 接口返回服务名与各依赖的连通状态；依赖不可达时仍返回结构化响应并标注不可用，不返回 5xx。

- **理由**：骨架阶段依赖可能尚未启动（尤其 ES 与 RabbitMQ），强校验会让"骨架是否可用"无法判断；结构化状态既能自检又不掩盖问题。
- **备选方案**：依赖不通就返回错误码 → 否决，会让首次启动体验变成排障。

### 决策 6：提供 Makefile 作为统一入口

提供 `make up`（启动中间件）、`make dev`（启动前后端）、`make health`（批量健康检查）。

- **理由**：命令散落在 README 里容易过时，Makefile 是可执行的事实来源，也便于后续 CI 复用。
- **备选方案**：只写进 README → 否决，命令易漂移。

## Risks / Trade-offs

- **goctl 版本与 go-zero 版本不匹配** → 缓解：决策 3 已给出降级路径，手写结构保持同样的目录与命名约定。
- **Elasticsearch 与 RabbitMQ 占用较多本地资源** → 缓解：compose 中标注为可选服务，可单独启动；health 对未启动依赖只标注状态。
- **Mantine 与 React 18 的版本兼容** → 缓解：初始化时锁定版本并写入 package.json，骨架阶段只渲染最小 provider 页面验证兼容。
- **骨架与基线规范漂移** → 缓解：任务 4.1 在骨架完成后逐条核对两个规范，把核对结果记录下来。
- **五个域同时建导致空目录较多** → 缓解：`rpc`/`model` 以占位文件说明职责，保持结构可读而非空目录堆积。

## Open Questions

无。骨架相关的关键选择已全部确定；业务域内的实体与表结构属于各自功能变更的范围，不在本设计内决定。
