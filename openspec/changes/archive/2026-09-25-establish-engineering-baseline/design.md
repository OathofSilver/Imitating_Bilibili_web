# Design

## Context

本变更的背景与动机见 `proposal.md` 的 Why 一节，此处不重复。

影响设计的关键约束：

- 代码量为零。所有约定都在落地之前固化，因此约束的成本最低，但一旦定错，纠正的代价会随代码增长而上升。
- 单人开发且技术栈异构：后端 Go 单体、前端 React SPA、四个中间件（MySQL、Redis、RabbitMQ、Elasticsearch）。没有多人分工来分摊规范维护成本，因此规范必须尽量靠工具强制而非靠人记住。
- 开发环境为 Windows，构建与测试在 Linux 容器中执行，行尾与路径差异是真实存在的失败源。
- 这些规范描述工程约束而非运行时功能，验收方式不是功能测试，而是结构检查、静态分析与流水线门禁。这一点必须在设计中明确，否则后续会有人误以为需要为「分层」写单元测试。

## Goals / Non-Goals

**Goals:**

- 让每条约束都有明确的承载者和验收方式：要么由工具强制，要么进入人工评审清单，不存在「写在文档里但没人检查」的约束。
- 让域边界在文件系统层面可见，使「单体但边界清晰」这一立场可被外部验证，而不只是口头声明。
- 让异步与缓存的正确性有可讲述的技术理由，而非跟风选型：事务边界与异步边界之间的关系必须能被推导出来。
- 让规范本身可演进：偏离基线必须以增量方式显式修改基线，不得静默绕开。

**Non-Goals:**

- 不包含任何运行时代码、目录骨架或配置文件实现。工程骨架由后续独立变更承担。
- 不定义具体功能需求（视频、弹幕、评论、关注等），本设计只约束这些功能如何被实现。
- 不规定具体框架 API 用法、库选型的版本细节与脚手架命令。
- 不引入微服务、服务网格、Kubernetes 等与「单体」定位冲突的编排复杂度。
- 不追求形式上的规范完备，不为覆盖率数字而增设约束。

## Decisions

### 决策一：后端目录采用垂直切域，而非全局水平分层

选择按业务域垂直成包（`internal/<domain>/` 内按角色命名的扁平文件），而非 `internal/handler/`、`internal/service/` 这类全局分层目录。

理由：域边界需要在文件系统上可见，「域间只经对方 service 接口」这条约束才有可执行的判定依据。全局水平分层下，跨域调用与同域调用在目录结构上完全无法区分，约束只能靠记忆维持。

域内保持扁平而不引入 `handler`/`service` 子目录，是为了避免目录数量随域数乘层数膨胀；单文件过大时以同包内新增文件解决，这是可逆的，后续若某域确实膨胀再升级为子目录也不影响其他域。

替代方案：全局水平分层（上手最快，但域边界不可见）；垂直切域加域内子目录（边界最硬，但目录膨胀且单人项目收益不足）。

### 决策二：HTTP 状态码与业务码双层，而非全部返回 200

选择让 HTTP 状态码表达传输、认证、限流与系统层语义，业务语义走 200 加非零业务码。

理由：错误率统计、告警阈值、熔断与依赖健康度全部建立在状态码维度上。全部返回 200 会使上述监控面板恒为空，等于主动放弃可观测性，而这恰好是本项目要展示的能力之一。

替代方案：全部 200 且语义只在业务码中（与部分真实站点行为一致，前端解析更统一，但监控维度丢失）。这个取舍的代价是前端需要在封装层同时处理状态码与业务码两层，已在 web 规范中要求统一处理。

### 决策三：对外标识一律字符串化

选择在所有对外响应与请求中将实体标识序列化为字符串，内部保持整型。

理由：标识生成器输出 64 位整数，超出前端数字安全整数范围，直接以数字序列化会静默丢精度并产生错误标识。这类缺陷在测试环境下通常不出现（数据量小、高位为 0），只在生产数据增长后暴露，属于典型的「上线后才炸」问题。

替代方案：前端使用大整数类型（引入额外依赖与转换负担，且任何遗漏转换的位置都会出错）；把标识设计得更短（牺牲生成器能力）。

### 决策四：列表接口默认游标分页

选择以游标分页作为默认，偏移量分页仅保留给后台场景。

理由：内容社区列表会持续插入新数据，偏移量分页在翻页时会因插入产生重复与漏项；同时大偏移量在数据量增长后会造成明显性能下降。游标分页同时解决了正确性与性能两个问题。

代价：无法直接跳页，且总数统计成本高，因此规范中明确允许省略总数字段而不返回估算值。

### 决策五：本地缓存必须配跨实例失效通道

选择允许使用进程内缓存，但强制要求通过订阅广播实现跨实例失效。

理由：本地缓存的收益在热点读上很明显，但多实例部署下若缺少失效通道，会出现「某实例长期返回旧值」的隐蔽不一致——写入方更新了数据，其他实例却毫不知情。这类问题排查成本极高，因为现象是偶发且与实例路由相关。

因此规范同时收窄了适用范围：只允许缓存变更频率极低且允许单机短暂不一致的数据。

替代方案：完全不使用本地缓存（少一层复杂度，但放弃多级缓存的讲述点）；使用本地缓存并接受短暂不一致（在多实例下不可接受）。

### 决策六：异步消息以事务内落表加事务外投递保证必达

选择要求消息生产走「权威数据源事务内写待投递记录，事务外投递」的方式，而非在事务内直接投递消息。

理由：在事务内直接投递消息存在双向不一致——事务可能回滚但消息已发出，或事务提交成功但投递失败导致消息永久丢失。前者会产生幽灵数据，后者会造成计数或索引长期缺失。而事务内禁止外部 I/O 这条约束本身也禁止了直接投递的写法，两条约束互为因果。

替代方案：事务内直接投递（实现简单，但无法保证一致性）；依赖消息中间件的事务消息能力（依赖特定实现，且与本项目的中间件选型不匹配）。

### 决策七：检索索引通过别名切换重建

选择索引名带版本后缀、对外只暴露别名，重建通过新索引加别名切换完成。

理由：中文分词配置与字段映射的调整往往需要重建索引，原地修改线上索引结构不可行。别名切换可以在不中断检索的前提下完成重建，同时为「全量重建修复长期不一致」提供了现成路径。

替代方案：直接使用固定索引名并在需要时重建（重建期间检索不可用，且回滚困难）。

### 决策八：集成测试自启依赖，不连接共享环境

选择由测试自身启动容器化的数据库、缓存、消息队列与检索引擎，而非连接开发者本机已安装的中间件。

理由：共享环境的既有数据会让测试结果依赖执行顺序，出现「单独跑过、一起跑失败」的偶发性失败；同时检索引擎需要分词插件，环境差异会造成测试在本地通过而在流水线失败。自启依赖使本地与流水线行为一致。

代价：首次执行需要拉取镜像，集成测试反馈较慢，因此用构建标签把它与快速测试隔离。

### 决策九：工程约束以能力规范承载，而非普通文档

选择把这些约束写成 OpenSpec 能力规范，并对新引入的概念保持少量：八项能力分别对应八个可独立演进、可被增量修改的约束集合。

理由：普通文档不会参与校验，也不会被增量追踪，因此对后续实现没有硬约束力。写成规范后，偏离基线必须以显式的增量修改表达，且能在流水线阶段暴露不一致。

同时引入一个区分原则作为贯穿全部规范的元规则：约束分为「可机器强制的」与「需人工判断的」两类。前者写入检查工具与流水线，后者进入评审清单。把需人工判断的塞进自动检查会造成误报并最终被绕过；把可机器强制的留给人工评审则一定会随时间失效。八项规范中的每条要求都按此原则归位。

### 决策十：规范校验进入流水线并启用严格模式

选择把规范校验作为独立的流水线阶段，失败即阻止合并。

理由：这是让规范真正生效的关键一步。若校验只在本地手工执行，规范会退化为「写了但没人跑」的文档。放入流水线后，提案与规范不一致、变更未声明能力等情况会在进入主干之前被拦下。

## Risks / Trade-offs

**[规范数量与严格度超出单人项目的维护能力] → 控制单条要求的判定成本，能交给工具的绝不写进人工清单；每条要求都保持简短且可被单点判定，避免出现需要综合判断的模糊要求。**

**[规范与实现开始漂移，流水线频繁因规范校验失败而变红] → 明确偏离的处理路径：以增量修改基线并在提案中说明原因，而不是降低校验强度或标记为可选项。变更与规范同步推进，不允许「先实现后补规范」。**

**[垂直切域在单域功能变多后出现超长文件] → 规范已给出升级路径：同包内按子功能拆文件，必要时再引入子目录。拆分不影响其他域，属可逆调整。**

**[双层状态码增加前端处理复杂度，且与部分真实站点的行为不一致] → 在 web 规范中要求前端在接口封装层统一处理两层，页面层不重复判断；同时在文档中记录该取舍的理由，避免后续被当作缺陷「修正」为全部 200。**

**[待投递记录表与投递协程引入额外复杂度] → 这是换取「数据写入与消息投递最终一致」的必要成本，且该模式是本项目要展示的异步可靠性能力之一，不作为可裁剪项。**

**[集成测试自启依赖导致流水线耗时增加] → 通过构建标签隔离，常规快速反馈不等待容器；流水线层面通过依赖缓存与并发取消缩短总时长。**

**[规范描述的行为无法被自动化验证，可能停留在纸面] → 每条要求尽量落到可检查的形式（静态规则、目录结构约定、流水线校验）；确实只能人工判断的，明确归入评审清单并在合并请求模板中提示。**

## Migration Plan

本变更只产出规范与项目上下文，不涉及运行时代码，因此没有部署与回滚步骤。落地过程为：

1. 本变更合入后，八项能力进入 `openspec/specs/`，成为工程约束的唯一事实来源。
2. 后续任何功能变更开始前，必须对照这八项能力检查提案是否与基线冲突；冲突时以增量方式修改基线，而非在实现中绕开。
3. 工程骨架与后续功能变更在本基线约束下展开，骨架变更需要逐条对照 `backend/layering` 与 `web/conventions` 落位。
4. 若发现某条要求在单人开发中确实不可维护，处理方式是以增量修改该要求并记录原因，不得在实现中静默违反。

回滚策略：本变更仅新增规范文件与上下文文件，回滚即丢弃对应文件与变更目录，不影响任何已有代码。

## Open Questions

- 业务逻辑层覆盖率的具体下限取值，可在工程骨架变更时依据实际可测代码量确定，不影响本设计中的其他决定。
- 前端端到端测试是否引入完整浏览器自动化，可待前端关键链路成型后再定，不影响本变更的任何要求。
