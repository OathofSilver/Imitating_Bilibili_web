# Project Context

本文件说明仓库的定位与边界。工程约束的唯一事实来源是 `openspec/specs/` 下的八项基线能力规范，本文件只描述「为什么是这样一个项目」，与规范冲突时以规范为准。

## 是什么

单体部署的类哔哩哔哩（bilibili）Web 端全栈项目。后端为一个 Go 进程（Gin 框架），前端为一个 React 单页应用，同仓库管理。

不是微服务，不拆服务，不引入服务网格或容器编排。

技术栈：

| 层 | 选型 |
| --- | --- |
| 后端 | Go + Gin |
| 前端 | React 18 + TypeScript + Vite 7 + Mantine + Zustand + React Router v7，包管理 pnpm |
| 主数据 | MySQL |
| 缓存 | Redis + 进程内缓存（go-cache） |
| 消息 | RabbitMQ |
| 检索 | Elasticsearch（go-elasticsearch v8）+ IK 中文分词 |
| 检索可视化 | Kibana 8.13 |
| 鉴权 | JWT |

## 给谁用

按重要性倒序，这个顺序决定了取舍方向：

1. **招聘方与面试官**：这是作品集项目，真实的验收方。关心的是分层是否讲得清、异步是否可靠、缓存一致性如何兜底、工程门禁是否真的在跑。
2. **UP 主**：叙事层面的用户，投稿、管理稿件、查看数据。
3. **观众**：功能层面的用户，浏览、播放、弹幕、三连、关注、收藏、搜索。

由此推导出一条取舍原则：任何「看起来专业但讲不出为什么」的做法都应砍掉，而能撑起技术讨论的链路要写厚。

## 解决什么

把「读多写少的内容社区」在单机单进程约束下的完整工程链路走通：

- 热点读路径的多级缓存（进程内缓存 → Redis → MySQL）与一致性兜底
- 热点写路径的异步化（Redis 累加 → 消息队列 → 落库）与最终一致
- 中文全文检索的索引设计、异步同步与降级
- 社交关系与信息流的分页与上限控制
- 工程可观测性：结构化日志与请求标识串联、限流、健康检查、流水线门禁

## 深度锚点

功能广度上不追求覆盖完整站点，覆盖不到的部分走「能跑通的薄实现」。技术深度集中在以下三条链路上，它们承担主要的展示职责：

1. 检索链路：索引设计、中文分词、异步同步、别名切换重建、深分页与降级。
2. 计数与互动链路：缓存累加、消息可靠投递、幂等消费、与主数据的对账。
3. 多级缓存一致性：进程内缓存与 Redis 的分层、跨实例失效广播、穿透与击穿防护。

## Non-goals

以下内容明确不在范围内。它们不是「以后再做」，而是不做：

- 视频转码、CDN 分发与自研播放器（使用预置媒体文件与浏览器原生播放能力）
- 推荐算法（使用规则热度排序，命名保持诚实，不使用「推荐」作为命名）
- 微服务拆分、容器编排、服务网格
- 支付、直播、会员购等商业化能力
- 弹幕实时推送之外的实时协作类功能

## 工程约束入口

八项基线能力规范：

| 能力 | 覆盖范围 |
| --- | --- |
| `backend/layering` | 分层模型、依赖方向、事务边界、跨域调用、目录布局 |
| `backend/coding` | 命名与注释、错误处理、日志、context、并发、序列化边界 |
| `api/contract` | 响应结构、状态码与业务码职责、错误码、标识序列化、分页、幂等、限流 |
| `data/platform` | MySQL、Redis、进程内缓存、RabbitMQ、Elasticsearch 的使用策略 |
| `web/conventions` | 前端目录、组件与状态边界、路由守卫、主题与样式、类型与封装 |
| `quality/testing` | 测试分层、覆盖率门禁、集成测试隔离、异步断言、验收判据 |
| `delivery/git` | 分支模型、提交规范、合并请求要素、禁止入库内容、行尾策略 |
| `delivery/ci` | 流水线阶段划分与门禁判定 |

任何功能变更的规范与设计都必须与上述基线保持一致。确实需要偏离时，必须以增量方式显式修改对应基线能力并在提案中说明原因，不得在实现中静默绕开。
